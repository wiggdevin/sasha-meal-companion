# Meal Companion — notes for any agent (Codex, Claude, Cursor)

Phone-first, multi-user PWA. It tells each person what to eat and when, lets meals be ticked off,
and builds every meal from that account's current foods and rules. Profile onboarding records the
inputs needed to derive a target candidate; the server revision remains authoritative.

## Source of truth for numbers
The latest effective server `target_profiles` revision is the sole authority for calories, macros,
floors, pins and approved proposals. `Settings.activeTargetProfile` is a display cache.
A viewed date resolves the revision in force on that date (`effective_from` ≤ date, highest `rev`;
before the account's first revision, none — the server's own `activeProfile` rule; a date the
180-date cap dropped resolves to the oldest kept revision, `Settings.targetHistorySince` holding the
first date) from the bounded `Settings.targetHistory`, rebuilt from
the mirrored `target_profiles` rows on every sync pass (`targetRevisionOn` in `lib/targets/revision.ts`);
its training weekdays set that date's day type. The current cache is the revision in force today by
the same rule (a future-dated revision waits in the history; with every revision future-dated the
cache is `needs_profile`), never simply the highest `rev`. A row with any malformed number is rejected, never read as 0;
a pass with no parseable row returns a cached revision to `needs_profile`, and a pulled delete leaves
the cache. The only cached revisions kept without a mirrored row are saved ones not yet pulled.
The server's "today" for target revisions is `lib/server/account-day.ts` (t24b): the phone's own
day when the request carries one (sync batches and `GET /api/targets?date=` send it), else the
account's stored `time_zone`, the request's zone, and UTC only as the logged last resort (never
the deployment-wide `HEALTH_TZ`, which would be a personal default); the phone re-resolves its cache at local midnight (`lib/targets/day-roll.ts`).
`lib/profile/derive.ts` may create a candidate only from a complete profile;
`lib/targets/{client,revision}.ts` persists and reads it. No ramp or numeric fallback exists. A
missing revision means `needs_profile`; plan resolution and the coach never invent targets.
The original PRD is in the parent planning archive; its first-client
target numbers are historical examples, not defaults for any account. **Every number a new account
starts from is its own** (ruling `docs/decisions/2026-09-22-target-priors.md`): conservative
activity factors 1.20–1.70, recomp at 0 %, and the expenditure engine seeded from that account's own
formula TDEE — never from the historical first-client analysis, which owns the first client's numbers only. The
open steps (body-fat provenance, rate-based goals, the static → adaptive handoff, the test suite)
are `docs/plans/2026-09-22-tdee-engine-plan.md`.

## Checkouts and the dev server
- The repo's own folder (`meal-companion/`) is the primary checkout and stays on `main`, fast-forwarded.
  Never leave it on a feature branch or with uncommitted work: park unfinished work on a pushed
  `wip/<date>-<topic>` branch before you stop.
- Feature work happens in a worktree: `git worktree add ../wt/<topic> -b <branch> origin/main`.
  Remove the worktree after its PR merges (`git worktree remove ../wt/<topic>`).
- The dev server on :3521 runs from the primary checkout via `pnpm dev --port 3521` (the dev entry in `.claude/launch.json`). `predev` fetches `origin/main`; in `next dev` a red banner says when the running code
  is behind main (`lib/dev/freshness.ts`, `components/DevFreshnessBanner.tsx`). A worktree's own
  server uses another port (3523+) and is stopped when its work lands.

**Order of operations for the T1 deploy: migrations and the annotate run go to production BEFORE the
PR merges, never after.** `lib/server/barcode.ts` and `lib/server/catalog.ts` select
`policy_categories` by name, so the deployed code errors against a database that has not had
`20261018090000`. An un-annotated catalog is the milder failure: `policy_categories` is
**nullable**, `NULL` means "never annotated", and every read path that holds the revision row —
the detail read, the barcode match and **food search** — derives the keys from
`lib/catalog/category-map.ts` instead (`policyCategoriesOf`, `lib/server/catalog.ts`). `'{}'` means
"annotated and clean" and is trusted as stored. So the switches keep their promise before the
script runs, and the script's corrections survive it afterwards. **Re-run
`scripts/annotate-policy-categories.ts --commit` once more after the app deploys**: a barcode scan
in the window between the migrations and the deploy is written by the OLD writer, which sends no
`policyCategories` key — the RPC stores NULL for those, so they derive correctly in the meantime,
and the second run annotates them properly.

## Rules that tests guard — keep them green
- Starter and suggested foods are filtered by the current account's explicit dietary rules.
  Historical ambiguous rules require review before seeding or suggestions. No generic account
  inherits the original client's gluten, dairy, apple, pouch or ritual preferences.
- Historical ritual slot ids and the `pouch` unit remain readable for explicitly saved data only.
  New account layouts generate `Meal 1` through `Meal N` from the account's admitted candidates and
  target: verified Eats in a closed food world; Favored and admitted universe foods in an open one
  (Phase 18 W8, `tests/meals/favored-never-limits.test.ts`, which also holds the open 30-date case).
- A food on Avoid never appears in any date's plan. In an open food world an Avoid mark on a family
  excludes every universe food of that family, at admission and, for a mark made on this device, at
  once (`tests/meals/open-world-layout.test.ts`, 365 dates).
- Favored favors and never limits in an open food world: a Favored food ranks higher, and a plate
  still uses another admitted food when that makes the better day (`tests/meals/favored-never-limits.test.ts`).
- A calorie change never moves the protein portion.
- Any date renders a complete day; there is no start date and no end date.
- Jev is never on the allergy path (Phase 18 W2a). Allergy decisions read deterministic evidence
  only: label or ingredient text, legacy tags, the food's name, stored non-Jev evidence, the
  whole-food class and the user's product check. A stored Jev-only flag (`listed`, `source = 'jev'`)
  is a hold: the food stays `unverified` ("Not verified") and is never `allowed`; only a logged
  review (`scripts/allergen-jev-holds.ts --review`) replaces it. Guarded by
  `tests/policy/facet-escalation-removal.test.ts`, including the check that no allergen decision in
  `lib/policy/` reads a Jev facet.
- Jev is never on the diet, religious or profile rule path either (Phase 18 W2c). Preference flags
  (`lib/policy/preference-marks.ts`) and profile hard rules (`lib/policy/profiles/hard-rules.ts`)
  read `lib/policy/diet-evidence.ts` only: the food's name and ingredient text, a tag that names the
  facet, stored non-Jev allergen evidence, stored `policy_categories`, the whole-food class and a
  verified starter's curated outcomes. A complete label blocks what it names but never clears an
  animal facet (`animal_product`, `meat`, `pork`, `beef`, `fish_seafood`, `shellfish`); it clears
  alcohol only. "Vegetable glycerin" and "shortening (palm)" stay unverified in v1; an ingredient
  parser (`lib/policy/diet-label.ts`) is a separate change with its own review. A food
  only Jev flagged is `unverified`, never `allowed`; a Jev `absent` clears nothing; a tag list that
  omits a facet is not proof of absence. Guarded by `tests/policy/diet-rule-jev-removal.test.ts`;
  the word-level decisions (a cut's species word, pescatarian, "eggplant", "beef tomato", oyster
  mushrooms) are pinned in `tests/policy/diet-evidence-edges.test.ts`. A non-allergen diet facet
  blocks with `facet:<facet>`, never `allergen:`. `scripts/diet-rule-jev-impact.ts` is the
  read-only per-account impact count (it takes no flag); the pre-merge run is
  `docs/audit/2026-10-05-w2c-impact.md`.
- Every generated candidate passes the D4 admission order before any score exists (Phase 18 W2b):
  only `allowed` foods with usable nutrition, less every Avoid family; ranking, similarity and Jev
  outputs order or connect admitted foods only. 500 random rule profiles over the full universe admit
  zero non-allowed foods (`tests/meals/open-world-safety.test.ts`).
- New suggestions need the current rule revision: a failed rule, Avoid or evidence read admits
  nothing, and an admission computed under an older `{ rulesVersion, evidenceVersion }` is never
  used (`tests/server/candidate-foods.test.ts`, `tests/foods/rules-freshness.test.ts`,
  `tests/migrations/food-world-clocks-db.test.ts`; the phone loader in `tests/foods/open-world-freshness.test.ts`).
- Ranking never changes a safety verdict (Phase 18 W7). The `pref-2` taste model
  (`lib/meals/preference.ts`) imports nothing beyond `lib/meals/occasion.ts`, reads only the
  soft-rule score (no hard rule, allergy or Avoid) and returns no verdict field; a taste dislike
  lowers rank and never excludes. With no taste values
  (`pref-0`, closed food-world accounts) `rankPlates` and `planDay` are byte-identical to Phase 17
  (`tests/meals/ranking-boundary.test.ts`, `tests/meals/pref2-baseline.test.ts`; formulas and
  monotonicity in `tests/meals/preference.test.ts`).

  `persistCompletedOnboarding` / `persistSkippedOnboarding`, first completion only) with 0
  default or inherited Favored marks. The open is durable (`lib/foods/world-open-client.ts`): a
  pending intent in the account's META store, re-posted after every successful sync
  (`lib/sync/post-sync.ts`) until the server answers 200 open, 423, 409 `condition_review` or
  another final 4xx. The retry sends `intent: "onboarding_default"`, which `setFoodWorld`
  (`lib/server/food-world.ts`) is one conditional write (`... where food_world_set_at is null`)

  production before this code merges**), so once the account is stamped the default changes

  retry can never re-open an account a person already decided about. It then answers 200 with the
  account's own world, and the phone clears the intent on `closed` as well as `open`. An explicit
  Settings POST (no `intent`) always applies and restamps. The legacy zero-food auto-seed
