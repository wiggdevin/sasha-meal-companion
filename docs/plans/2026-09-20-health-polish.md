## 2. Contracts (fixed here so parallel tasks agree)

### 2.1 Units (landing 1)
- Storage stays metric: `user_settings.height_cm`, `weight_kg`. Two display preferences, independent, additive nullable columns `user_settings.height_unit ('ft_in'|'cm')` and `weight_unit ('lb'|'kg')`, defaults `ft_in` and `lb`, carried through `_sync_upsert` with the omit/null contract and the phone `Settings` cache (`lib/sync/user-settings.ts`, `lib/types.ts`).
- One pure module `lib/units/height.ts` (+ weight helpers where they already exist in `lib/health/units.ts`): `cmToFtIn(cm) → {ft, in}` (inches rounded to the nearest whole, carry 12 → ft+1), `ftInToCm(ft, in)` (×2.54, 1 decimal), `formatHeight(cm, unit)`, validation 50–260 cm, ft 3–8, in 0–11. Round-trip property test: `ftInToCm(cmToFtIn(x))` within 1.3 cm for every integer cm in range.
- Shared control `components/HeightField.tsx`: `<HeightField valueCm={number|null} unit={"ft_in"|"cm"} onChange={(cm: number|null) => void} onUnitChange={(u) => void} />` — owns the segmented control and the inputs; onboarding and Settings both mount it; the weight equivalent is `components/WeightField.tsx` with `valueKg`/`lb|kg`.
- Height field UI (onboarding body step AND the Settings Profile row): a segmented control `ft / in | cm` (≥ 44 px), two numeric inputs (feet, inches) in ft/in mode, one in cm mode; switching converts the displayed value, never the stored one; the input keeps `inputmode="numeric"`. Weight fields use the weight unit everywhere pounds are printed today (`app/page.tsx`, `components/BodyDashboard.tsx`, `app/week/page.tsx`, `components/WeightTrend.tsx`, `components/coach/attachments/WeighInField.tsx`, onboarding default).

### 2.3 Multi-day meals and titles (landing 2; from the D2 probes)
```ts
// lib/coach/actions.ts — set_slot_meal v2 (superset; single-date callers unchanged)
type SetSlotMealAction = {
  type: "set_slot_meal";
  from: string;                // YYYY-MM-DD in the request timezone (was `date`; `date` accepted as alias)
  through?: string;            // inclusive; default = from; from..through ≤ 31 calendar days else the action is rejected with a reason
  weekdays?: (0|1|2|3|4|5|6)[];// filter after expansion; 0 = Sunday
  slot: SlotId;                // named by label in the prompt: meal-1 = Breakfast, meal-2 = Lunch, meal-3 = Dinner …
  title: string;               // the dish name, 1–40 chars after sanitizing on the live wire (the model MUST supply it; storage columns allow 80 so a user-typed title has headroom — ruling 2026-09-20)
  items: GroundedItem[];       // grounded ONCE
  dates: string[];             // filled by the server after expansion (never by the model); the phone materializes one plan_days override per date
};
// log_meal gains `title: string` (same rule); LogCommitRequest and log_entries gain a nullable `title`;
// SlotOverride / plan_days item overrides gain `title`; resolveDay overlays meal.name from it.
```
Title rule: the dish name is the card title everywhere (`SlotCard`, `LoggedExtras`, reconciliation); the slot is the badge/colour and secondary text. When a title is missing the client derives one from item names ("Sourdough toast, bacon & eggs"), never `Snack`/`Breakfast`/`Meal · N items`, for new rows. Undo for a series restores every prior override in one composite token; a failed date rolls back the dates already written. A later edit to one date changes only that row; a logged entry is never deleted by a plan edit. Jev intent taxonomy gains `plan_meal` (no fast path; routing only).

### 2.4 Apple Health activity and adaptive targets (landing 3) — adopted from design round 2 (`~/.claude/goal-state/sasha-health-polish/lanes/D6b/design-v2.md`, the detailed contract; driver ruling 2026-09-20, no third round)
Boundaries (held): device active energy is a demoted observation — never a TDEE fallback, never a food allowance, never "eat back"; steps never add kcal, widen a clamp, raise confidence, bypass `held`, or change a proposal directly; no automatic activity multiplier — a step band may only prompt a user-approved edit of the existing categorical `activityLevel`; `target_profiles` revisions stay the numbers authority.
Engine `exp-2.0.0` (conceded): the weight-trend smoother may use `ALPHA_CORROBORATED = 2/11` instead of `ALPHA = 2/21` only when (1) the ordinary engine result is neither `burn_in` nor `held`, (2) the activity band is `lower|higher`, (3) the base pre-clamp residual `baseRaw − prior` already moves ≥ 10 kcal in the band's direction, and (4) the fast candidate moves farther in that direction; both EMAs consume the identical accepted/interpolated series; the selected raw value then goes through the unchanged order prior ±10 % → confidence blend → 0.9–2.2 × BMR → round to 10. `usual`, `insufficient`, disagreement or < 10 kcal agreement is byte-for-byte the base path. Version bump + backtest record mandatory (five worked scenarios: drop, usual, rise, disagreement, logging gap; artifact fixtures keep the 5 % water-swing and 21.4 % cycle bounds).
