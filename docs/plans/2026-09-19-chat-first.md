## 1. Contracts (fixed here so parallel tasks agree)

### 1.1 Attachments (request to `POST /api/coach`, optional field `attachment`)
```ts
type CoachAttachment =
  | { kind: "barcode"; v: 1; gtin14: string; foodRefId: string; revisionId: string; localDate: string; slot?: string; scannedAt: string }
  | { kind: "capture"; v: 1; method: "photo" | "label"; mediaPath: string; localDate: string; slot?: string };
```
A turn with an `attachment` carries the user's `content` (may be empty; the server stores a canonical line such as "Scanned a barcode" / "Sent a photo"). The user row persists the attachment (compact reference only) in `tool_calls.attachments`. Idempotency, sequence and rate limits are the existing `/api/coach` ones.

### 1.2 UI blocks (`lib/coach/ui-blocks.ts`, Zod, versioned; persisted in the assistant row's `tool_calls.blocks`)
```ts
type LogDraftBlockV1 = {
  kind: "log_draft"; v: 1; id: string;
  source: "barcode" | "capture"; method?: "photo" | "label";
  localDate: string; slot?: string;
  draft: CaptureDraft;            // the existing propose/barcode draft shape (items with foodRefId/revisionId, name, grams or portion, nutrients, unverified flags)
  policy: { blocked: boolean; reason?: string; blockedItemIds?: string[] };
  status: "pending" | "committed" | "dismissed"; entryIds?: string[];
};
// Phase B
type ChartBlockV1 = { kind: "chart"; v: 1; id: string; chart: "weight_trend" | "macros_today" | "kcal_week"; days?: number; series: { label: string; points: { x: string; y: number }[] }[]; unit: string; caption: string };
type QuickRepliesBlockV1 = { kind: "quick_replies"; v: 1; id: string; options: string[] /* 2..4, ≤ 40 chars each, sanitized */ };
type FoodSearchBlockV1 = { kind: "food_search"; v: 1; id: string; query: string; intent: "log" | "eats" | "avoid"; results: { foodRefId: string; revisionId: string; name: string; kcalPer100g?: number; status: "eats" | "avoid" | "neutral"; blocked?: boolean }[]; truncated: boolean };
type FoodIdeasBlockV1 = { kind: "food_ideas"; v: 1; id: string; ideas: ComposedMeal[] /* the existing suggest_options cards */ };
type UiBlock = LogDraftBlockV1 | ChartBlockV1 | QuickRepliesBlockV1 | FoodSearchBlockV1 | FoodIdeasBlockV1;
```
The client renders through a registry `components/coach/blocks/<kind>.tsx`; an unknown kind or version is omitted and the text stays readable. Block buttons call the existing action/commit/list paths; a block never writes on its own. The model never authors hydrated data.

### 1.3 Message view (response + thread history)
`CoachMessageView { id; role; content; seq; createdAt; attachments?: CoachAttachment[]; blocks?: UiBlock[]; actions?; composed? }` — the thread route selects `tool_calls`, validates blocks with `uiBlockSchema`, and adapts legacy `composed` cards.

### 1.4 Capabilities
`AppCapabilities { coach: boolean; scan: boolean; captureMethods: ("photo"|"label"|"voice"|"text")[] }`, computed server-side from `COACH_ENABLED`, `NEXT_PUBLIC_FEATURE_SCAN`→`FEATURE_SCAN` (server-read), `CAPTURE_METHODS`; passed from the root layout through a context. `NEXT_PUBLIC_COACH_ENABLED` is removed. Fail-closed: a missing variable means off.

### 5.1 Principles (D4/D6, the 2026-09-14 and 2026-09-15 rulings, F10; NEW = added here, S = changed by Sol)
- Jev routes, judges and ranks. It never writes text, never does arithmetic, never invents a serving or converts a unit. Code owns every number and every threshold.
- Every Jev call is fail-open on the SERVICE side (timeout 3 s, 4xx/5xx, malformed → today's behaviour) — but S: fail-open never turns an unknown judgment into "allowed". Under an active hard preference an unknown facet is `unverified`, shown as "Not verified".
- Logging marks, never refuses. A Jev judgment on a log or draft adds a mark or a warning; it never removes the item or refuses the commit. Recipes, plans and automatic suggestions (things she PLANS) omit blocked and unverified items; an explicit user choice may still proceed through the existing marked/confirmation path.
- The server writes no user state during a coach turn. NEW: the facet cache is not user state, but S: it is filled OFF the interactive path only (import, creation, warmer). No scan, capture, search, log commit or coach reply waits for a facet judgment.
- S (F10 rewritten): Jev may receive the current user-authored utterance under the existing provider disclosure (`docs/ai-data-handling.md`) and minimal canonical food fields. Stored conditions, weight, gut data, notes, `diet_prefs.text` and stored preference flags never enter Jev state. Reply verification is skipped on any turn that read profile, gut, weight, target or note context. Matching a person's flags against food facets happens in server code.
- S: deterministic evidence wins. Precedence: the gluten/dairy/apple floor and the Avoid list → ingredient allergen tags → stored `policy_categories` → Jev positive judgment. Jev may ADD evidence; it never clears stronger evidence, and it never overwrites a stored `user_food_prefs.role`.
- NEW: judgments are reusable data — one judgment per exact food identity per facet per rubric version, consumed by every surface.
- S: one request-scoped budget of THREE logical Jev calls shared by intent, ranking, sanity and verification; a retry does not consume a slot; facet warming is not an interactive call. Jev is under the same daily spend cap as Gemini.
- S: no fixed launch thresholds. Per-question, per-action present/absent/abstain thresholds are frozen from a development split (C6b) and reported on an untouched holdout; level probabilities (not a fractional Score) gate actions.
- Every Choice has an explicit no-match option (`none` / `unstated`).

### 5.2 Contracts (S = Sol's revised contract adopted verbatim in substance)
**Facet vocabulary v1** (`lib/foods/facets.ts`, `FACETS`; each an atomic Noul about the FOOD only; `rubric_version` starts at 1):
```
human_food | requires_preparation
breakfast_fit | lunch_fit | dinner_fit | snack_fit
meat | fish_seafood | shellfish | animal_product | pork | beef | alcohol
contains_gluten | contains_dairy | contains_egg | contains_peanut | contains_tree_nut | contains_soy | contains_sesame
raw_cruciferous | raw_leafy_greens | onion_garlic | beans | simple_sugars
```
`high_fodmap` is NOT in v1 (food-, preparation- and portion-dependent).
**Storage (S)** — migration `food_facets(food_key text, input_hash bytea, facet text, rubric_version int, p numeric(4,3) not null, model text not null, judged_at timestamptz not null default now(), user_id uuid null, primary key (food_key, input_hash, facet, rubric_version))`. Shared keys are `catalog_revision:<id>`; user foods are keyed `user_food:<id>:<rev>` with `user_id` set. `input_hash` = sha256 of the canonical name, brand, description, preparation state and available ingredient text. RLS: service role only; application reads go through authenticated SERVER paths. No client reads the cache directly.
**Service (S)** — `readFacets(keys)` is cache-only and is the ONLY API interactive paths may call. `ensureFacets(foods)` runs at catalog import (`scripts/annotate-policy-categories.ts` gains a facet pass), at barcode resolve and user-food creation (after the response is sent, best effort), and from an idempotent warmer (`scripts/warm-facets.ts`, resumable, takes `adminClient()`). Batches are sized by measured serialized tokens and question count with ≥ 50 % headroom under the vendor budget, never by a food count. Failure leaves explicit unknowns and never throws. `purpose: "food_facets"`.
**Facet rules (S)** — `lib/policy/facet-rules.ts`: vegetarian → meat, fish_seafood, shellfish; vegan → animal_product (+ vegetarian's); pescatarian → meat, pork, beef; no_pork → pork; no_beef → beef; no_shellfish → shellfish; no_eggs / no_soy / no_peanuts → ingredient evidence first, Jev `contains_*` as additional positive evidence, missing evidence = unverified; low_fodmap → the authored `onion_garlic` and `beans` evidence only; halal → known pork/alcohol rejected, otherwise unverified unless certification/preparation evidence exists; kosher → known pork/shellfish rejected, otherwise unverified likewise.
**Conditions (S)** — `lib/policy/condition-rules.ts` is EMPTY in v1 with a header stating the rule: a diagnosis never activates a food facet or a dietary warning. Additions require nutritionist-approved evidence, exact user-facing copy, applicability boundaries and a labelled evaluation (owner step; see 5.6). A user-confirmed `low_fodmap` preference operates on its own.
**Verdicts (S)** — a facet outcome is `present | absent | unknown` by its frozen per-facet, per-action thresholds. `PolicyVerdict` gains `unverified` (unknown evidence required by an active preference) and `marks: {facet, p?, source: "floor"|"avoid"|"ingredient"|"category"|"jev", outcome}[]`. Logs always commit and visibly mark blocked or unverified items. Automatic suggestions, recipes and plans exclude blocked and unverified items.
**Sanity (S + Q10)** — `lib/log/sanity.ts`: deterministic checks on PER-SERVING amounts after code handles count, unit and recipe/batch context (grams ≥ 2000 or kcal ≥ 3000 per serving → `implausible`; grams < 2 → `tiny`). Jev asks `not_human_food` (cache first) and atomic portion-level questions only on explicit request or ASYNCHRONOUSLY after the draft renders; nothing delays attachment creation or "Log it". Drafts carry `sanityStatus: "checked" | "deterministic_only" | "unavailable"` and `warnings: {itemId, kind: "not_food"|"portion", level, message, suggestedGrams?}[]`. Serving identity (Q10): when a logged item matches a catalog food with several portions or a serving history, code lists the candidates and Jev picks ONE by Choice (options = the candidates + `none`); code preserves brand, raw/cooked state, unit and exact grams. Thresholds ship only from C6b.
**Suggestions (S + Q8)** — code removes deterministic blockers and cache-known facet blockers before ranking and withholds applicable unknowns as unverified. The ONE ranking call receives candidate foods/macros, the exact app slot id/label and only the current request's wish — never stored flags or `diet_prefs.text`. Stored flags are matched in server code. No-cook uses stored `no_cook` first; Jev judges `requires_preparation` only when evidence is absent. Rank stays code-owned. Role (Q8): for a food with no stored role, one advisory Choice `meal_component_role` {protein_anchor, carb_source, fat_source, produce_or_free, mixed_dish, none} on state `{food:{name, description, prepState}, nutrientBuckets:{protein, carb, fat}}` (buckets computed by code); the user confirms before persistence; a stored role always wins.
**Onboarding (S)** — the existing call adds Choice `cooking_effort` {none, minimal, full, unstated}; flags and cooking effort stay confirmable suggestions; the chips copy: "Confirmed preferences filter recipes and meal ideas when the food is verified. Foods we cannot verify are marked Not verified. You can always log what you ate."
