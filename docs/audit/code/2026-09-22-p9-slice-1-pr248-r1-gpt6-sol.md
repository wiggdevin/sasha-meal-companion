[BLOCK] **Ownerless legacy data can be assigned to the wrong account.** `lib/device/legacy-adoption.ts:174-206` infers the phone’s owners from records that happen to carry IDs, then `lib/device/legacy-adoption.ts:223-243` copies the ownerless store, drafts, and scans when it finds just one. The first user’s ID can then be the sole recorded owner, exposing the second user’s meals or notes. Keep ownerless data held until its owner can be established through a safe recovery flow. Test a shared phone where B leaves local-only data and A is the only recorded owner.

[BLOCK] **The retained Oura GET route bypasses the account boundary.** `app/api/health/oura/start/route.ts:28-30` still creates OAuth state for a headerless GET; `lib/server/auth.ts:32-38` accepts a missing account header. The old client calls that GET by navigation (`origin/main:lib/health-client.ts:130-134`). If an old A tab invokes it after the shared cookie changes to B, the route starts the connection as B. Reject headerless GET before `startOura`, or require verifiable account ownership. Test the old-tab, B-cookie path; the existing POST-only test does not cover it.

[BLOCK] **A late session result can rebind the gate to the wrong user.** `components/AuthGate.tsx:315-318` applies the initial `getSession()` result even after a newer auth event has applied another session. Its onboarding read then queries `user_settings` without an expected user ID (`lib/profile/onboarding-state.ts:127-133`), and `components/AuthGate.tsx:292-311` can cache the returned disposition under the stale ID. Ignore stale initial results, bind each read to a session generation, filter by expected `user_id`, and recheck the handle before applying it. Test a delayed A result after a B sign-in event.

Capture one handle at entry, pass it through the weigh-in and target calls, and assert it before every later read, write, and callback. Test a switch while the weigh-in response is pending.

Capture the initiating handle and use checked reads and `saveStoreFor` after each await. Test switches during profile sync and target reset.

The latter calls cache operations without a handle (`lib/barcode/scan-cache.ts:22-32`), so their default becomes the current account (`lib/db/catalog-cache.ts:74-90`). A switch in that gap can place A’s food reference and policy verdict in B’s cache. Carry the original handle through lookup, cache, offline fallback, and resolution; reject settlement after a switch and test that interleaving.
