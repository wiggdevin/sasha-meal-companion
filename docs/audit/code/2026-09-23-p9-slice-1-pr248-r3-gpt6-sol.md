1. [BLOCK] **Old tabs can still expose or write another account’s data.** `lib/server/auth.ts:32-38` accepts requests without `x-smc-account`. The old export link (`origin/main:components/ExportCard.tsx:59-70`) sends no header, while `app/api/export/route.ts:152-163` exports data for the current cookie’s user. An A tab can therefore download B’s data after another tab signs in as B; the same gap permits headerless weigh-in writes (`app/api/health/weigh-in/route.ts:53-63`). Require the account header on account-data routes and test an old A tab with B’s session. The service-worker reload does not prove every old request has stopped.

2. [BLOCK] **A lost response can replay an older target over an accepted correction.** `lib/targets/client.ts:193-209` restores the previous queued revision after any ordinary error from a direct send. If the server accepted the newer revision but its response was lost, the older revision remains queued and later becomes authoritative. Keep the newer idempotent request until its outcome is reconciled; test server acceptance followed by transport failure.

3. [BLOCK] **A queued target restore is not idempotent.** `lib/targets/client.ts:66,291-298` queues a restore with a request ID but omits that ID from the POST body. `app/api/targets/route.ts:59-63,131-134` and `lib/server/targets.ts:172-190` create another revision on replay. An accepted restore whose response is lost at an account switch can replay after a newer revision from another device and override it. Make restores idempotent by durable request ID, or reconcile server authority before replay.

4. [BLOCK] **Concurrent same-day weigh-ins can erase a newer correction.** `lib/health/weigh-in-client.ts:158-163,267-281,358-392` checks that a queued weight is newest *before* sending, but does not order an already in-flight 170 lb request against a subsequent 171 lb save. If 171 reaches the server first, the later-arriving 170 overwrites it; both requests can then leave the local queue. The RPC’s upsert is last-writer-wins (`supabase/migrations/20261019090000_manual_weigh_in.sql:96-104`). Add a durable per-day ordering check at the server and test responses arriving in reverse order.
