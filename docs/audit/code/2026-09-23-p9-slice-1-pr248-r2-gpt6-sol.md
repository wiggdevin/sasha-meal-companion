1. [BLOCK] **Onboarding can write A’s profile into B’s account.** `lib/profile/onboarding-client.ts:199-209` awaits A’s weigh-in, then calls `saveSynced` before checking A’s handle. On an A→B switch, `saveMorningWeight` returns `null` (`lib/today/water-and-weight.ts:251-258`), and `saveOnboardingSettings` captures B as its new owner (`lib/profile/onboarding-client.ts:84-98`). B can receive A’s target and settings. Carry A’s handle through the entire operation and check it immediately after the weigh-in await, before any further write. Test that interleaving.

2. [BLOCK] **Switching accounts erases local-only coach action and Undo state.** `lib/device/forget.ts:20-21,64-75` deletes every `coach:*` cache for the departing account. That cache contains action status and Undo tokens (`lib/coach-client.ts:30-35`); server thread restoration supplies messages without those actions (`components/coach/CoachShell.tsx:111-116,181-190`). Even a single-account sign-out loses them. Preserve action-bearing state, or make it recoverable before treating the cache as disposable. Test A→B→A with an applied action and Undo token.

3. [BLOCK] **The legacy sweep deletes coach action records whose owner cannot be verified.** `lib/device/legacy-adoption.ts:139,151-160` removes old `smc:coach:*` transcripts and `smc:coach-action:*` marks. The old build used those marks to remember applied results (`origin/main:lib/coach/apply-client.ts:30-31,49-55`); the new build cannot reconstruct them from server messages. This violates the chosen hold-without-deleting treatment of ownerless device data. Move both key families into held legacy storage and add a migration test that proves their bytes survive.

4. [BLOCK] **A switch after server acceptance can replay an older health or target value.** If A has a pending 170 lb weigh-in, then saves 171 lb, a switch after the server accepts 171 but before the response reaches `accountFetch` prevents retirement of 170 (`lib/device/account.ts:107-110`; `lib/health/weigh-in-client.ts:237-257`). On A’s return, `runDrain` posts 170 (`lib/health/weigh-in-client.ts:312-342`), and the same-day upsert reverts the correction. The target queue has the analogous window: an unacknowledged newer revision leaves an older pending body to be posted as a later revision (`lib/targets/client.ts:193-200,205-225`; `supabase/migrations/20261023091000_target_revision_transactions.sql:19-26`). Reconcile queued entries against authoritative server state or a durable latest-intent sequence before replay; test acceptance, switch, and return for both queues.
