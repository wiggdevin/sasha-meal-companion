## Source review notes

- `_sync_upsert` writes `plan_days` with `insert … on conflict do update`. The BEFORE INSERT
  trigger runs on the proposed row and the BEFORE UPDATE trigger runs on the update, so both
  paths are guarded. The update `SET` reads `p_payload`, not `excluded`, so the update trigger is
  the one that decides the stored value.
- `plan_days` delete and restore are not sync kinds (`apply_sync_op` allows them only for
  `user_foods`, `log_entries`, `gut_log`), so a tombstone cannot drop history.
- Lock order is the same in log, undo and the generic write: `plan_days` row, then
  `recipe_consumed_slot_state`. Log and undo take `recipe_plan_state` first; the generic write
  does not touch it. No cycle.
- Behaviour to know, not a defect: after an online undo, a device that did not see the undo and
  ticks that slot offline (no epoch) gets `applied`, and the guard restores the undo mark. The
  device converges on its next pull; the offline tick is not kept.
