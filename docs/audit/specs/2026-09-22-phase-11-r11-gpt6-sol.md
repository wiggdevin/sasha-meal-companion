Verdict: DO NOT SHIP — 1 BLOCK, 3 FIX, 1 NIT

1. [BLOCK] **The 30-day purge date is user-controlled.** The proposed trigger only rejects a change from non-null `deleted_at` to null ([spec:417](/Users/zero-suminc./projects/clients/Sasha/meal-companion/docs/specs/phase-11-conversations-memory.md:417)). Authenticated owners retain `INSERT` and `UPDATE` on `coach_threads` ([RLS:17](/Users/zero-suminc./projects/clients/Sasha/meal-companion/supabase/migrations/20260911000500_rls.sql:17)). They can insert or update a chat with a past timestamp for immediate purge, or move an existing tombstone into the future. Have the database set the timestamp on first deletion, reject later changes by authenticated users, and reject or normalize a non-null timestamp on insert. Test direct PostgREST writes.

2. [FIX] **Resume can miss the latest messaged chat.** The spec changes only the response access and says no other resume logic is needed ([spec:365](/Users/zero-suminc./projects/clients/Sasha/meal-companion/docs/specs/phase-11-conversations-memory.md:365)). The existing consumer excludes chats with null `lastMessageAt` ([CoachScreen.tsx:61](/Users/zero-suminc./projects/clients/Sasha/meal-companion/app/coach/CoachScreen.tsx:61)), while the create route permits empty chats ([route:37](/Users/zero-suminc./projects/clients/Sasha/meal-companion/app/api/coach/threads/route.ts:37)). Fifty newer empty chats can fill page one and hide the latest messaged chat on page two. Define whether resume selects an empty chat; if it does not, query for the latest messaged chat separately or page until one is found. Test that case.

3. [FIX] **A lost delete response leaves the deleting device’s cache behind.** The proposed handler evicts only after a successful DELETE response ([spec:455](/Users/zero-suminc./projects/clients/Sasha/meal-companion/docs/specs/phase-11-conversations-memory.md:455)). If the server commits but the response is lost, a retry returns 404 because the route only updates an active thread ([route:62](/Users/zero-suminc./projects/clients/Sasha/meal-companion/app/api/coach/threads/[id]/route.ts:62)); the cache is never removed. Treat that 404 as confirmation that the requested thread is gone, clear its cache and open transcript, and test a committed delete followed by a lost response.

4. [FIX] **The preview can show content that is no longer the latest message.** It changes only on message `INSERT` ([spec:325](/Users/zero-suminc./projects/clients/Sasha/meal-companion/docs/specs/phase-11-conversations-memory.md:325)), but authenticated owners can directly `UPDATE` or `DELETE` their messages ([RLS:55](/Users/zero-suminc./projects/clients/Sasha/meal-companion/supabase/migrations/20260911000500_rls.sql:55)). Editing, moving, or deleting the latest message leaves stale preview text. Maintain the preview for those mutations, or revoke unsupported direct mutations, and test the resulting list row.

5. [NIT] **The stated cache aging path does not exist.** The spec says `CACHE_LIMIT` can age out a cached thread ([spec:473](/Users/zero-suminc./projects/clients/Sasha/meal-companion/docs/specs/phase-11-conversations-memory.md:473)). It limits messages *within each thread* to 50; it does not evict thread keys ([coach-client.ts:102](/Users/zero-suminc./projects/clients/Sasha/meal-companion/lib/coach-client.ts:102)). State that an unopened copy may remain until that device opens it or clears its storage.
