# Audit: phase-11 round 2 (GPT-6 Sol, codex exec, xhigh, read-only)

Target: `docs/specs/phase-11-conversations-memory.md` · Commit: `b1bd4fa` · Date: 2026-09-22 20:46 MDT

---

Verdict: DO NOT SHIP — 10 BLOCK, 5 FIX, 0 NIT

1. [BLOCK] **The sweep cannot trust `coach_messages.user_id`.** Phase 11 takes the account ID from a swept message and writes through `adminClient()` (`docs/specs/phase-11-conversations-memory.md:308-322`). Current RLS permits an authenticated user to insert or update a message in their own thread with a different `user_id`; it checks the thread owner, not that column (`supabase/migrations/20260911000500_rls.sql:55-68`; `20261001000000_phase7_coach.sql:19-24`). The proposed citation columns are nullable, so their same-account trigger does not close every path. Bind message ownership to the thread in the database, restrict client writes to sweep-controlled fields, and derive the sweep account from the verified thread owner. Test a forged direct PostgREST row.

2. [BLOCK] **An Edit bypasses the medical-memory rule.** The revised policy allows direct authenticated updates to `text` and `kind` (`docs/specs/phase-11-conversations-memory.md:214-219`), and §4 explicitly skips the judge for edits (`:432-435`). A user can turn an existing row into medical text through PostgREST, contradicting the absolute success criterion at `:638-639`. Route edits through a validated endpoint and apply the same medical screen, or change the guarantee and storage policy explicitly.

3. [BLOCK] **Deleting a memory still does not stop unsolicited use in its original thread.** The narrower copy promises the coach stops bringing it up on its own (`docs/specs/phase-11-conversations-memory.md:437-449,640-643`). The thread summary is injected automatically on every turn (`lib/server/coach-threads.ts:116-131`; `lib/coach/history.ts:106-123`), and the prompt tells the model to carry preferences forward (`lib/coach/prompt.ts:110-118`). Deleting only `coach_memories` leaves that automatic source intact. Invalidate or suppress affected summary content on deletion, with a same-thread next-turn test.

4. [BLOCK] **The authoritative-state fix still permits a stale goal.** The spec allows “I want to lose weight before the wedding” as `goal_context` (`docs/specs/phase-11-conversations-memory.md:342-356`). If the user later changes their structured goal, that prose remains. The proposed “YOUR DAY wins” instruction cannot resolve every conflict because the profile line is fetched only when `needsProfileContext` permits it (`lib/server/coach-context.ts:187-198`). Link goal memories to a revision and invalidate them on goal changes, or always supply current goal state wherever those memories are used.

5. [BLOCK] **“Forget everything” is not fenced against the race it claims to fix.** The worker reads `forgotten_at` *before* writing (`docs/specs/phase-11-conversations-memory.md:312-318`); it can read the old value, then insert after the forget transaction commits. The state table also gets pattern-1 authenticated write access (`:478-484`; `supabase/migrations/20260911000500_rls.sql:5-22`), allowing its fence value to be changed or removed directly. Make the state service-managed and serialize the fence check and memory mutation with the forget operation in a database transaction. Test that exact interleaving.

6. [BLOCK] **The durable work intent is still not an idempotent processor.** A null `remember_processed_at` makes both `afterResponse()` and the daily sweep eligible to process the same message (`docs/specs/phase-11-conversations-memory.md:301-311`). Both can observe no matching memory and insert; a crash after one of up to three candidate writes but before the marker also replays partial work (`:228-231,275-279`). Specify a transactional claim, stable per-candidate identity, and atomic write/processed-state transition. Test concurrent workers and interruption after candidate one.

7. [BLOCK] **The recall verifier still has no recall results in its proposed evidence path.** Phase 11 builds evidence from `toolCalls[i].result` (`docs/specs/phase-11-conversations-memory.md:403-418`). Current turn code attaches `result` only when a tool produces a persisted UI block (`lib/server/coach-turn.ts:731-733`); ordinary read tools fall through with `block: null` (`lib/coach/blocks/index.ts:173-197`). The verifier also returns one combined `flagged` value today (`lib/coach/verify.ts:24-57`), while the spec needs different handling for write and recall claims. Capture bounded recall results independently of UI-block persistence and return separate verdicts for the two checks.

8. [BLOCK] **A deleted thread can still receive an in-flight turn or a replay.** Adding `deleted_at is null` to `resolveThread()` checks only before the model call (`docs/specs/phase-11-conversations-memory.md:176-181`; `lib/server/coach-turn.ts:233-239`). Deletion during that call does not prevent later `persist()` inserts (`lib/server/coach-threads.ts:159-177`). `storedTurn()` also returns before `resolveThread()` runs, so retrying an already saved message can return a deleted transcript (`lib/server/coach-turn.ts:233-237`). Recheck active status atomically when persisting, and apply the deleted-thread rule to replay.

9. [BLOCK] **The purge conflicts with Phase 10’s onboarding foreign key.** Phase 11 includes onboarding threads in the list and plans to hard-delete thread rows after 30 days (`docs/specs/phase-11-conversations-memory.md:154-156,171-174`). Phase 10 retains one `onboarding_drafts` row per account with `thread_id references coach_threads`, without a delete action (`docs/specs/phase-10-conversational-onboarding.md:349-353`). A referenced onboarding thread cannot be purged as specified. Decide whether it is deletable, then define a safe draft detach or cascade rule and test purge of completed and incomplete onboarding threads.

10. [BLOCK] **The contradiction fix only compares memories assigned the same kind.** The spec’s “vegetarian” → “I eat meat now” reversal is still not guaranteed: the first candidate can be `preference` and the second `fact`, so they never meet (`docs/specs/phase-11-conversations-memory.md:198-201,267-279`). Both could then be injected as active dietary guidance. Compare across kinds for dietary and goal contradictions, or give such memories a stable topic key; test the reversal with different assigned kinds.

11. [FIX] **The list’s preview and browser search paths are unspecified.** Every row must show a one-line preview and search old message text (`docs/specs/phase-11-conversations-memory.md:154-160,502-508`), but the current list response has only ID, title, kind, and time (`app/api/coach/threads/route.ts:23-31`), and the proposed search module is server-side. Define the owner-scoped browser endpoint/client method and the latest-message preview query, including deleted-thread filtering.

12. [FIX] **The account-memory fetch is missing from the named read path.** Slice 3 names a `CoachContext` field and renderer (`docs/specs/phase-11-conversations-memory.md:613-615`), while `buildCoachContext()` currently loads day, lists, recipes, profile, and activity only (`lib/server/coach-context.ts:182-198`). Explicitly add the owner-scoped active-memory query there and test the full database-to-prompt path.

13. [FIX] **Citation clearing is not atomic with soft deletion.** The spec says to update memories “right after” the existing thread update in the same request (`docs/specs/phase-11-conversations-memory.md:182-189`). The current delete is one completed database request (`app/api/coach/threads/[id]/route.ts:62-67`); a second request can fail after the thread is already deleted. Use one transactional RPC or an equivalent database operation, and test failure rollback.

14. [FIX] **The proposed reference trigger does not cover every relationship.** It checks `source_thread_id` and `source_message_id` for matching users (`docs/specs/phase-11-conversations-memory.md:202-226`) but does not require a cited message to belong to the cited thread or `superseded_by` to point to the same account. Enforce both relationships in the database and test mismatched references through service-role writes.

15. [FIX] **A sixth shrink step is not a hard context cap.** Dropping account memory last (`docs/specs/phase-11-conversations-memory.md:331-338`) leaves the output over 2,500 tokens whenever the existing five steps already do (`lib/server/coach-context.ts:249-267`). Add a final bounded fallback or state the cap as a best-effort target; test a base context that exceeds the cap before memory is added.
