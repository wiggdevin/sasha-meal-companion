Verdict: DO NOT SHIP — 4 BLOCK, 6 FIX, 0 NIT

1. [BLOCK] **A name-only Avoid does not reach the food policy.** The spec calls unmatched Avoids safe (`docs/specs/phase-10-conversational-onboarding.md:488-495`), but `set_food_membership` writes preferences only for existing refs and caps catalog matches at 50 (`supabase/migrations/20261023090400_food_membership_v2.sql:25-56,107-120`). Policy checks a ref preference, not `food_membership_revisions` (`lib/policy/constraints.ts:141-142`). An unmatched or truncated Avoid can therefore be suggested later. Apply the name rule in every policy path, including newly created refs, or tell the user it is not yet enforced. Test zero-ref and over-50-ref names.

2. [BLOCK] **A catalog-only Eat cannot join phone rotation as promised.** The spec says an existing catalog ref with nutrients is enough (`docs/specs/phase-10-conversational-onboarding.md:488-493`). The phone projection loops over `user_foods`, not catalog refs (`lib/store.ts:274-300`), and rotation reads that projection (`lib/rotation.ts:171-194`). Either add a catalog projection with verified nutrients and a role, or list every catalog-only Eat as needing details and make no rotation promise.

3. [BLOCK] **“Looks right” is not bound to the build the user saw.** The turn commit may accept `p_build` on a stage-8 turn and set `summary_confirmed_rev` on “Looks right” (`docs/specs/phase-10-conversational-onboarding.md:423-437`). Completion checks the draft revision and value ranges, but specifies no immutable build version or check that `build.target_revision` matches its confirmed profile fields (`:450-475`). Persist the displayed build as an immutable snapshot; make approval reference that snapshot without accepting field changes, and derive the target from it. Test an edit during approval and an edit after the summary.

4. [BLOCK] **The specified backup change would break nightly backups.** Both new tables lack an `id` column (`docs/specs/phase-10-conversational-onboarding.md:412-421`), while the backup job orders every table without a `COMPOSITE_KEYS` entry by `id` (`app/api/jobs/backup/route.ts:55-74`). Adding only their names, as specified at `docs/specs/phase-10-conversational-onboarding.md:529-530`, makes the job fail. Add keys for both tables and test backup and restore. Include `food_membership_revisions`, currently absent from `TABLES` (`app/api/jobs/backup/route.ts:36-48`), because it can be the only record of a name-only mark.

5. [FIX] **The Health status contract cannot supply the stage-3 values.** It returns counts and latest dates (`docs/specs/phase-10-conversational-onboarding.md:338-343`); the existing daily response has steps, energy and body mass, but no height or body-fat value (`lib/health/contract.ts:93-105`). Specify an owner-scoped read of the saved values, units, sample dates and source used for the read-back and target derivation. Test that another account’s source yields no data.

6. [FIX] **Preview reset leaves the same device stale.** Reset deletes server rows and the change feed (`docs/specs/phase-10-conversational-onboarding.md:556-563`), but the client retains its account cache, outbox and cursor. A pull from the old cursor cannot discover deleted rows; the changes route returns that cursor when no rows follow it (`app/api/sync/changes/route.ts:40-44`). Purge and rebind the Preview account’s device state as part of reset, or use a new invited account per run. Verify skip-all on the same device shows no old foods or target.

7. [FIX] **The new admin-backed Preview routes lack explicit cross-user proof.** Reset and fake backfill use privileged writes (`docs/specs/phase-10-conversational-onboarding.md:556-566`), while Phase 9 requires every admin entry point in its manifest with a second-user canary test (`docs/specs/phase-9-tenancy-blank-slate.md:655-660`). Add both routes and tests proving account A cannot read or change B’s draft, Health sources or other rows.

8. [FIX] **Reconnect can leave a working token attached to the wrong pending source.** Two Connect calls can each issue a new source token (`docs/specs/phase-10-conversational-onboarding.md:318-320,344-348`; `app/api/health/tokens/route.ts:26-34`). Without serialization, the Shortcut may retain one token while the draft polls the other source. Make connect idempotent or lock the draft while revoking, issuing and assigning the source; test a double tap and reload.

9. [FIX] **The target-date rule still permits an impossible estimate.** It requires an amount and chosen rate, then uses `effectiveRatePctWeek` (`docs/specs/phase-10-conversational-onboarding.md:217-220`). A calorie minimum can make that effective rate zero or opposite the selected goal (`f743cfb:lib/profile/rate-goal.ts:63-70`). Show a date only when the effective rate moves toward the stated amount; otherwise explain the bound.

10. [FIX] **The scan-date question omits the year.** The spec asks for month and day before storing `body_fat_measured_on` (`docs/specs/phase-10-conversational-onboarding.md:258-261`). Katch eligibility depends on the exact calendar year and a 180-day window (`f743cfb:lib/profile/energy.ts:79-93`). Ask for and confirm the full date before assigning a measured source.
