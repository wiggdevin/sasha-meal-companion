1. [BLOCK] **Confirmation can disappear on replay.** The spec adds `needs_confirm` and says the server sets `confirm`, but does not define a persisted field that survives action validation. The current grounded schema strips unknown fields, and a returned action enters `pending` by default ([spec:124](/Users/zero-suminc./projects/clients/Sasha/meal-companion/docs/specs/phase-12-coach-tools.md:124), [actions.ts:498](/Users/zero-suminc./projects/clients/Sasha/meal-companion/lib/coach/actions.ts:498), [chat-state.ts:113](/Users/zero-suminc./projects/clients/Sasha/meal-companion/lib/coach/chat-state.ts:113)). Specify a server-owned confirmation field in the grounded and replay schemas, and initialize restored actions from it. Test a `log_weight` retry and reload before Confirm.

2. [BLOCK] **The proposed meal policy permits blocked foods.** `plan_range.set_slot_meal` is to be checked “like today,” but today’s grounding keeps blocked ingredients and only marks them; `applySetSlotMeal` saves them ([spec:204](/Users/zero-suminc./projects/clients/Sasha/meal-companion/docs/specs/phase-12-coach-tools.md:204), [ground.ts:131](/Users/zero-suminc./projects/clients/Sasha/meal-companion/lib/coach/ground.ts:131), [apply-slot.ts:65](/Users/zero-suminc./projects/clients/Sasha/meal-companion/lib/coach/apply-slot.ts:65)). Reject blocked ingredients for a *planned* meal. Recheck current food preferences and constraints at Confirm, since they can change during the 15-minute preview.

3. [BLOCK] **The floor test checks a calorie sum, not the resulting macros.** A day can exceed the sum of minimum calories while its actual fat or carbohydrate grams fall below their individual floors ([spec:146](/Users/zero-suminc./projects/clients/Sasha/meal-companion/docs/specs/phase-12-coach-tools.md:146)). This matters here: calorie adjustment uses a fixed 80 g rest-day carbohydrate floor while derived revisions carry a 100 g carbohydrate floor ([types.ts:276](/Users/zero-suminc./projects/clients/Sasha/meal-companion/lib/types.ts:276), [derive.ts:129](/Users/zero-suminc./projects/clients/Sasha/meal-companion/lib/profile/derive.ts:129)). Validate the final training and rest macro grams against the active account floors at the server write, and preserve any stricter active floors in the new revision.

4. [BLOCK] **The offline calendar precedence claim is false.** The spec says B’s untouched fields survive A’s later range write ([spec:243](/Users/zero-suminc./projects/clients/Sasha/meal-companion/docs/specs/phase-12-coach-tools.md:243)). B’s queued `plan_days` payload carries the whole row, including fields it did not edit; conflict merge chooses the newer side for every field both rows define ([plan-day-client.ts:109](/Users/zero-suminc./projects/clients/Sasha/meal-companion/lib/plan-day-client.ts:109), [merge.ts:30](/Users/zero-suminc./projects/clients/Sasha/meal-companion/lib/sync/merge.ts:30), [outbox.ts:182](/Users/zero-suminc./projects/clients/Sasha/meal-companion/lib/sync/outbox.ts:182)). A later server timestamp can erase B’s unrelated note. Record field-level intent and merge it, or show a conflict instead of promising survival.

5. [BLOCK] **An absent calendar row has no apply-time lock.** The proposed RPC locks touched rows `FOR UPDATE` before comparing them with the preview, but that locks nothing for a date whose preview said “absent” ([spec:232](/Users/zero-suminc./projects/clients/Sasha/meal-companion/docs/specs/phase-12-coach-tools.md:232)). The existing sync writer uses a per-user, per-entity, per-date advisory lock precisely to serialize that read/write boundary ([phase3_sync_entities.sql:428](/Users/zero-suminc./projects/clients/Sasha/meal-companion/supabase/migrations/20260919090300_phase3_sync_entities.sql:428)). Require the range RPC to take those same locks in sorted date order before checking absence or revision; test concurrent Confirm and first edit on an empty date.
