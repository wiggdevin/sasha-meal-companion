Verdict: DO NOT SHIP — 5 BLOCK, 0 FIX, 0 NIT

1. [BLOCK] **A profile change can write targets against the old profile.** The spec says the settings sync op precedes the target write (`docs/specs/phase-12-coach-tools.md:124-126`). Current coach and Settings profile flows write targets first, then queue settings locally (`lib/coach/apply-profile.ts:135-142`; `components/settings/use-settings-controller.ts:53-75`; `lib/sync/settings.ts:49-70`). The database can therefore validate the old row and store a floor below the profile that syncs afterward. Require a server acknowledgement of the profile change before derivation and target writing, or make both one server transaction. Define the offline ordering too.

2. [BLOCK] **Table grants bypass the proposed safety boundary and weaken its version check.** Authenticated users retain owner-scoped `INSERT`, `UPDATE`, and `DELETE` on both `target_profiles` and `user_settings` (`supabase/migrations/20260911000500_rls.sql:8-22`). A phone can insert a below-floor target without calling the protected RPC; it can also change floor inputs in `user_settings` without advancing `rev`. That contradicts the writer and stored-profile guarantees (`docs/specs/phase-12-coach-tools.md:107-112,284-286`). Revoke direct target writes and make every permitted profile mutation advance a trusted version, or compare the floor inputs themselves under the lock.

3. [BLOCK] **Adding RPC parameters leaves the old callable signatures in place.** The installed writers take `(uuid,jsonb)` and `(uuid,jsonb,jsonb)` and grant execution to `authenticated` (`supabase/migrations/20261023091000_target_revision_transactions.sql:3,71-87`). The spec says they “gain” two parameters but does not require dropping or revoking those old signatures (`docs/specs/phase-12-coach-tools.md:93-111,276-280`). PostgreSQL will treat the new signatures as overloads, leaving an unchecked route. Specify the dependency replacement and explicit removal or revocation of both old signatures; test direct authenticated calls to each.

4. [BLOCK] **Proposal approval still uses a potentially stale floor.** The spec passes the active revision’s stored minimum plus the current settings revision (`docs/specs/phase-12-coach-tools.md:113-115`). The approval function reads that active minimum and writes it into the proposal revision (`supabase/migrations/20261023090500_approve_proposal_via_revision.sql:25-30,60-70`). A later weight or profile change can raise the account’s `macroMinimumKcal` while the active revision retains its old floor; matching `settings.rev` does not prove the floor value is current. Compute the shared TypeScript floor for approval from current stored inputs and pass it through the checked writer, with a changed-weight approval test.

5. [BLOCK] **The profile-row lock does not serialize weigh-in changes.** The writer compares the latest weigh-in while holding `user_settings` (`docs/specs/phase-12-coach-tools.md:98-106`), but manual weigh-ins and health ingestion write `health_samples` without that lock (`supabase/migrations/20261019090000_manual_weigh_in.sql:96-104`; `supabase/migrations/20260925000000_phase5_health_ingest.sql:103-115`). A newer weight can commit after comparison and before the target transaction commits, leaving a target checked against the older floor. Coordinate every weigh-in write and deletion with the target check, or use a versioned weight source that the transaction can validate.
