Verdict: DO NOT SHIP — 5 BLOCK, 2 FIX, 0 NIT

1. [BLOCK] **The onboarding thread is writable outside the serialized turn path.** The spec relies on `onboarding_commit_turn` locking the draft and assigning message sequence numbers (`docs/specs/phase-10-conversational-onboarding.md:503-524`). The existing coach route accepts any owned thread ID without checking `kind` (`lib/server/coach-threads.ts:98-108`), and authenticated users can insert or edit messages in their own threads directly (`supabase/migrations/20260911000500_rls.sql:53-68`). A normal coach request or direct write can interleave with onboarding messages. Restrict normal coach turns to `chat` threads and prevent direct authenticated writes to messages in `onboarding` threads; test both paths.

2. [BLOCK] **The approved target cannot be checked against all the profile inputs as specified.** Completion claims to compare the target revision’s sex, birth year and height with the approved profile (`docs/specs/phase-10-conversational-onboarding.md:544-549`), but PR #241’s `TargetInputs` contains none of those fields, nor body-fat provenance (`f743cfb:lib/types.ts:56-66`). The summary flow also says TypeScript computes a build from the draft *after* committing it while SQL inserts that build in the same transaction (`docs/specs/phase-10-conversational-onboarding.md:503-516`). Specify how the route passes the build into that transaction, store the full canonical derivation-input snapshot, and verify it against the approved profile before writing the target. Test a mismatch in sex, birth year, height and body-fat provenance.

3. [BLOCK] **The first turn has no serialization point.** The proposed function locks the draft row, but creates that row only on the stage-1 turn (`docs/specs/phase-10-conversational-onboarding.md:503-527`). Two first turns can both observe no row; the unique draft or onboarding-thread constraint then makes one fail instead of returning the promised `412`. Two simultaneous retries with the same `client_turn_id` can also pass the pre-lock replay check before either inserts its result (`:493-509`). Take a per-user transaction lock before initialization, then recheck the turn ID and revision under that lock. Test concurrent first turns and concurrent same-ID retries.

4. [BLOCK] **Preview enables invites before Phase 9’s required migration.** Phase 10’s Preview setup enables invite signup after Phase 9 slices 1, 4, 5 and 6, and explicitly allows slice 8/M2 to follow (`docs/specs/phase-10-conversational-onboarding.md:789-794,826-829`). Phase 9 says M2 is required before any invited account exists (`docs/specs/phase-9-tenancy-blank-slate.md:602-611`) and places it before invite activation (`:769-778`). The current constraint rejects an invited account’s `breakfast` eaten mark (`supabase/migrations/20261026090000_plan_days_eaten_slots.sql:6-14`). Require Phase 9 slice 8 and its acceptance gate before Phase 10 invite-based Preview tests or activation.

5. [BLOCK] **The specified backup still omits the schedule Phase 10 writes.** Phase 10 adds three onboarding tables and `food_membership_revisions` to the nightly backup (`docs/specs/phase-10-conversational-onboarding.md:630-636`), but its one-time build also replaces rows in Phase 9’s `day_templates` and `template_slots` (`:303-359`). The backup’s fixed table list has no template tables or `account_claims` (`app/api/jobs/backup/route.ts:36-48`; Phase 9 schema at `docs/specs/phase-9-tenancy-blank-slate.md:477-502`). A successful nightly job would omit the user’s customized rhythm. Add those account-owned tables and their child rows to the backup inventory, then restore a completed custom-template account in the integration test.

6. [FIX] **Reconnect does not invalidate an in-flight Health turn or an approved build.** Connect locks the draft and changes `pending_health_source_id`, but specifies no revision bump or approval clearing (`docs/specs/phase-10-conversational-onboarding.md:370-380`). A turn can read samples from the old source outside its lock and still pass the unchanged revision check (`:398-409,502-509`); reconnect after “Looks right” likewise leaves the old build approved. Increment `rev`, clear `confirmed_build_id`, and verify the pending source under the commit lock whenever Connect rotates it. Test both races.

7. [FIX] **Saving a name does not make the ordinary coach use it.** The spec adds `display_name` to `profileLine` so the coach can greet the user (`docs/specs/phase-10-conversational-onboarding.md:597-607,819-824`). Today `buildCoachContext` includes that line only for profile actions or weight/target questions (`lib/server/coach-context.ts:96-104,182-196`). Specify a separately fetched name in ordinary turns; do not enable the whole health profile line for every turn. Test the first general chat after onboarding.
