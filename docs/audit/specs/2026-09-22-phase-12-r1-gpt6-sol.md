1. [BLOCK] **Existing actions bypass the new confirmation rule.** The spec keeps `set_slot_meal` for up to 31 dates while requiring confirmation only for `plan_range` over seven dates. Existing `update_profile` can change goal and body facts, and `log_weight` can trigger a target revision; both currently apply from `pending` without confirmation. Route *every* existing and new action through the server’s confirmation policy, including range size and the fields inside `update_profile`. 4. [BLOCK] **The server calendar RPC is not reconciled with queued phone edits.** `plan_days` has an IndexedDB mirror, outbox, and local Today projection. A pulled server row is withheld while that date has a pending op; a later conflict is rebased field by field. The proposed RPC writes directly to Postgres without coordinating those states, so a confirmed range can silently displace a queued edit or remain invisible on that phone. Specify flush/conflict handling, mirror projection, and undo behavior for devices with pending edits; test that sequence. Define replacement or deletion semantics with item tombstones or a whole-entry revision conflict, then test concurrent edits and Undo.
