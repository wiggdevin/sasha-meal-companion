Verdict: DO NOT SHIP — 4 BLOCK, 1 FIX, 0 NIT

1. [BLOCK] **Invalid percentage splits can be saved.** The spec removes `validatePercentProfile` without replacing its 100% check (`docs/specs/phase-12-coach-tools.md:161`). The route schema bounds each percentage separately (`app/api/targets/route.ts:18-29`); the sum check lives in the validator being removed (`lib/targets/percent.ts:55-70`). Keep server-side percentage-sum validation independent of the new floor check.

2. [BLOCK] **Authored calorie requests can change silently.** The spec tells the writer to replace a submitted calorie value with 4/4/9 calories from the grams (`docs/specs/phase-12-coach-tools.md:161`). A request for 2,000 kcal with 150 g protein, 200 g carbs and 80 g fat would store 2,120 kcal. The current conversion derives rest-day carbs separately from the requested rest calories (`lib/targets/percent.ts:78-95`). Define that conversion for both day types, then reject a request that cannot meet its chosen calories and the minima; do not silently save a different calorie target.

3. [BLOCK] **The weight-staleness check has no complete payload path for existing target operations.** The check compares both kg and sample ID (`docs/specs/phase-12-coach-tools.md:113-120`), but current derive payloads contain no sample ID (`lib/server/targets.ts:54-81`), authored writes use `user_settings.weight_kg` (`lib/server/targets.ts:258-273`), and restore copies a historical revision’s inputs (`lib/server/targets.ts:172-190`). A current sample can therefore make valid writes fail with `SF003`; treating an absent ID as “skip” would leave the promised check ineffective. Specify how each operation obtains and carries the selected server sample, including how restore checks today’s floor while retaining the historical macros.

4. [BLOCK] **A stale queued target can retry forever.** The new writer returns `SF003` when the selected weight changes (`docs/specs/phase-12-coach-tools.md:113-120`), but the spec changes queue settlement only for `below_floor` (`docs/specs/phase-12-coach-tools.md:212-215`). Today the drain retains every failed entry (`lib/targets/client.ts:202-218`). Define settlement for queued `build_stale`: rebuild from the current weight with a new request ID, or retire the stale entry with a visible notice. Test a queued retarget followed by a newer weigh-in.

5. [FIX] **Align the onboarding error description.** The caller table says Phase 10 turns `below_floor` into `build_stale` (`docs/specs/phase-12-coach-tools.md:163`), while Phase 10 correctly handles `SF001` without an automatic retry and reserves that retry for `SF003` (`docs/specs/phase-10-conversational-onboarding.md:894-902`). Correct the table so implementation and tests use the same rule.
