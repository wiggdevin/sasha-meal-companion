# Meal Companion — Feature List

This is the full feature list. It covers what the app does today and what the
architecture v2 plan adds. Phase 0 marks both the original build (before
phases existed) and the v2 "Foundations" phase, since v2 migrates this exact
data. Phases 1–8 follow `v2 §1` and `v2 §8`.

Columns: **ID** · **Feature** · **Detail** (exact behavior) · **Phase** (0–8)
· **Disposition** (exists / planned / deferred / rejected) · **Source**
· **Acceptance** (one testable sentence).

**A backticked path is a claim.** An `exists` row ends its Source cell with the implementing file
in backticks. A `planned` row names no existing file in backticks **anywhere in the row** — not in
Detail, not in Acceptance either; where the gap is known it is stated after `— missing:`, in plain
words. `pnpm lint:docs` (`scripts/check-features.ts`) reads every cell and fails when a `planned`
row names a file that exists, or an `exists` row names one that does not. Every row was re-checked
against the code on 2026-09-17 (T9 §3) except F-065, which lands on its own branch — that pass is
what retired the 2026-09-14 Loop 010 note that this column could not be trusted.

What the guard can see: **backticked text only**, and only tokens carrying one of the repo's file
extensions (`.ts`, `.tsx`, `.js`, `.jsx`, `.mjs`, `.cjs`, `.sql`, `.py`, `.sh`, `.css`, `.svg`,
`.json`, `.md`, `.yml`, `.yaml`), with or without the `@/` prefix the code imports by. A path
written without backticks, a bare directory, or a name with no extension is invisible to it — deliberately, because guessing whether a word is a path is
how a linter starts lying. A claim you want checked has to be written as a backticked path.

**Known and accepted.** `components/TabBar.tsx`'s hydration mismatch is closed by PR #141, with
`tests/tabbar/body-capability-first-paint.test.tsx` as the regression test; the residual cold-cache
the Body destination stays reserved even while its capability resolves, so primary navigation never shifts.

## Deferred and rejected

**Deferred** (not rejected — parked, with a stated condition to revisit):

- **F-109 Native shell (Expo + HealthKit)** — deferred because the PWA + Shortcuts path is unproven; a native shell adds app-store and maintenance overhead not justified yet (v2 §1, Phase 8).
- **F-110 Garmin sync** — deferred because the Garmin developer program is on hold (v2 §1).
- **F-112 Health Connect sync** — deferred because it needs a native Android shell, which is itself deferred (v2 §1).
- **F-113 Withings direct scale sync** — deferred because weight already arrives via Apple Health; a direct integration is redundant unless the user gets a non-Apple-connected scale (v2 §1, §10).
- **F-114 Real web push notifications** — deferred because the `.ics` calendar approach needs no server, no VAPID keys, and no cron running unattended for months; push is the fallback only if the calendar route fails in practice (PRD §4).
- **F-115 Supplement tick (creatine)** — deferred pending the reviewer's answer on whether the user is already taking it (PRD §9.7, §12).
- **F-091 Weight trend line** — gated, not fully deferred: hidden until estimator status leaves `burn_in` and until 20 weigh-ins exist, so an early noisy trend cannot mislead the user's about the user's real TDEE (v2 §4.3, PRD §9.8).
- **F-116 ChatGPT web connector** — deferred; Codex is the supported MCP client today, and OAuth/no-auth wiring for ChatGPT was never done (AGENTS.md).

**Rejected** (considered and explicitly ruled out, not merely parked):

- **F-111 Fitbit / Google Health sync** — rejected because the Fitbit API retires 2026-09-30; building on it now would build on a dying API (architecture.md §1, v2 §1).
- **"Week 4 autonomy mode"** — a date-triggered behavior switch at day 22 of a programme. Rejected because the unbounded, date-keyed design has no day 22 to switch on; the always-on shift-times and per-day-training-toggle capability (F-009, F-010, F-011) replaces it for less code (PRD §7.4).
- **`startDate` config field** — rejected/removed. The unbounded, calendar-date-keyed design (F-016) makes a programme start date unnecessary and actively wrong to show the user's (PRD §1.1).
- **Social features** — rejected as a non-goal for a single-user app; no social surface fits the product (PRD §9, "Deliberately excluded").
- **Streaks-as-guilt mechanics** — rejected. The design goal is neutral, non-scolding framing, especially around Floor Day; a streak-guilt mechanic works against that (PRD §7.2, §9).
- **"Programme complete" / day-counter framing** (e.g. "day 14 of 28") — rejected. There is no programme, only dates; a completion or countdown screen contradicts the core simplifying decision (PRD §1.1, §10).
- **PRD-era exclusion of calorie search / barcode database** — the original PRD (2026-09-07) explicitly excluded a searchable food database and barcode scanning because "the user is not tracking, the user is following" (PRD §9, "Deliberately excluded"). The 2026-09-10 brief reverses this: it asks for a full nutrition tracker with USDA-backed search and a barcode scanner. That reversal is now the plan of record — see F-024 (exists, current food-db search), F-050–F-057 (Phase 1 catalog and search), and F-062 (Phase 3 barcode scanner).
